> 类型：CLAUDE.md 记忆纪律规则完善（经验层/规则层，不改拓扑）
> 裁决人：optics_agent CC（人工审查后落，非 E-flow 自动）
> 状态：pending（待本轮跑完，由 optics_agent CC 落到 SEPR CLAUDE.md）

## 现象（真跑观测）

step03 spawn 的 sub-agent 因 tools allowlist（`Read,...,Skill`，无 MCP）结构性无法调 `memory_*`/`ToolSearch`，只能落 `.work/memento-cache/` JSON，由 main-agent（有 MCP）代回灌。sub-agent 报告把这描述为"allowlist 设计与记忆红线的内在矛盾"。

## 定性（optics_agent CC 裁决）

**不是矛盾，是分层设计的正确结果被误读成 bug。** 两条都是刻意的：
1. 子 agent MCP 全量注入占 60k+ context → allowlist 排除 MCP 是 CLAUDE.md 写死的设计；
2. 执行层 sub 独立写长期记忆会制造 case 级半成品污染全局库 → 本就不该让它写。

正解 = main 代理记忆是**设计不是 workaround**，要扶正成显式规则。

## 落地建议（改 SEPR CLAUDE.md「记忆要求」节，双写 .human）

把记忆纪律按层区分：

- **编排层（main-agent / evolution-agent）**：持 memento（tools 含间接 MCP 途径或本就在编排层跑）。职责：开工搜记忆；spawn 前把相关记忆摘要放进 sub 的 spawn 指令；回收 sub 的 `.work/memento-cache/*.json` 后**审查去污染**再 `memory_store` 回灌（哪些 case 结论进全局、哪些原始细节只留 case 文件夹）。
- **执行层（sub / sub-e）**：结构性无 MCP（allowlist 已排除）。职责：不直接写长期记忆；把"本该存的记忆"落 `.work/memento-cache/<case>-<step>.json`（带 provenance 五要素），交回编排层。**报告里不再要求"结束前 memory_store"，改为"结束前落 memento-cache JSON"**。
- **叶子层（sub-leaf / sub-e-leaf）**：同执行层，只落 cache 不写全局。
- 现有 MCP 预检第 0 步保留（编排层用；执行层预检对象改为"memento-cache 目录可写"）。
